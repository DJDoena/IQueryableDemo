# QueryableTest — Chat History Summary

## Goal
Build a hands-on example to understand `IQueryable` vs `IEnumerable` using a `Car`/`Storage` model, fully hand-rolled (no `AsQueryable()`, no built-in `Where`), so every step can be debugged.

Debugged into `CarSqlQueryProvider.Translate` and confirmed the hypothesis: since `CarSqlQueryable<T>` is both `IQueryable<T>` and `IEnumerable<T>`, passing an already-compiled delegate (rather than a lambda convertible to `Expression<Func<Car, bool>>`) makes the `IEnumerable<Car>` overload of `WhereExtensions.Where` bind instead of the `IQueryable<Car>` one - no `Where` `MethodCallExpression` is ever appended, so `Translate` receives only the bare root `ConstantExpression` and filtering falls back to plain client-side enumeration via `WhereExtensions.GetWhereIterator`. Distinguished this "invalid"/bypassed case from the legitimate recursive base-case hit (reached from inside the `Where` `MethodCallExpression` case while resolving `whereCall.Arguments[0]`) by comparing call stacks - the caller of `Translate` is `Execute<TResult>` directly in the bypass case, vs. `Translate` itself (recursing) in the valid case.
